1) **Открытый MD-файл не обновляется на лету, когда агент его правит.** Если заметка/файл открыт в просмотрщике и агент меняет её на диске, в окне остаётся старая версия — приходится закрывать и открывать файл заново, чтобы увидеть изменения.
   - По коду: события `fs-changed` / `notes-changed` доходят и обновляют деревья (`FileTree.tsx`, `NotesTree.tsx`, `AppStore.tsx`), но содержимое уже открытого документа по ним не перечитывается.
   - Ожидаемое поведение: открытый файл сам перечитывается с диска, когда меняется внешним процессом (агент, другая программа), без закрытия/открытия.
   - Сохранить позицию скролла и, если возможно, курсор — чтобы обновление не «дёргало» текст.
   - Если в файле есть несохранённые правки пользователя — не затирать их молча: показать «файл изменён извне» с выбором «обновить / оставить моё».

2) **Ответ агента обрывается при переключении вкладок — нужна фоновая работа и параллельные чаты.** Пишу в чат (в Harness, в проекте, в «Заметках и файлах» — неважно) и, пока агент отвечает, переключаюсь на другую вкладку. Возвращаюсь — ответа нет, процесс не продолжился.
   - Нужно: начатый ответ продолжает генерироваться в фоне независимо от того, какая вкладка открыта. Возвращаюсь в тот чат — вижу либо уже готовый ответ, либо живой процесс генерации с того места, где он сейчас.
   - Пользователь должен иметь возможность разослать запросы в несколько чатов одновременно и потом просто ждать: все они считаются параллельно, каждый в своём чате, без взаимных блокировок.
   - Индикация: у чатов, которые работают в фоне, видно статус (точка/спиннер в списке чатов), чтобы было понятно, где ещё идёт работа и что ответ готов.
   - По коду сейчас: состояние прогона живёт в хуке компонента чата (`useChatRun.ts` — подписки `onAgentEvent`, очередь сообщений, флаги `running`), при уходе с вкладки компонент размонтируется, подписки снимаются и поток событий теряется — поэтому возврат показывает пустоту. Нужно вынести состояние прогона на уровень выше (общий store по `chatId`) и держать подписки смонтированными, а не привязанными к конкретному виду.
   - Ожидаемое поведение: смена вкладки/экрана не влияет на выполнение; одновременно может работать несколько чатов; вернувшись, всегда видно актуальный результат или текущий прогресс.

3) **Клик по расписанию стирает историю чата: остаётся только вопрос «что это за расписание» и ответ на него.** Открываю расписание из панели — вся предыдущая переписка этого чата исчезает, вижу только последнюю пару сообщений.
   - По коду причина найдена: `openSchedule` в `components/harness/HarnessView.tsx` делает `setActiveId(sessionId)`, затем сразу `dispatch({ type: "send", … })` с вопросом «объясни, что это за задача по расписанию». В редьюсере (`chatShared.tsx`) `send` ставит срезу `loaded: true`, а эффект догрузки истории пропускает сессию, если `stateRef.current[id]?.loaded` уже true — то есть `harnessSessionHistory` для неё вообще не вызывается. Плюс правило `loaded` при живом прогоне специально не перезаписывает `items`. Итог: старые сообщения никогда не подгружаются, в чате остаются только этот вопрос и ответ.
   - Ожидаемое поведение: при открытии расписания чат сначала показывает свою полную историю, и только потом (или уже поверх неё) идёт вопрос-пояснение с ответом.
   - Авто-вопрос «что это за расписание» не должен выглядеть как начало нового чата: он дописывается в конец истории.
   - Если у расписания ещё нет своей сессии — допустимо создать новую, но тогда это должен быть честно новый чат с заголовком по расписанию, без видимости «пропали старые сообщения».
   - Решение: если история уже есть (обычный случай), авто-вопрос не отправляется; чат просто открывается с историей. Авто-вопрос — только для реально пустой/новой сессии.

   - Удаляю расписание → удаляется и чат, в котором оно было поставлено.
   - Всё это — только после подтверждения в модальном окне с «Подтвердить / Отменить», как сейчас при удалении обычного чата; в тексте окна честно перечислять, что именно уйдёт вместе с объектом (например «Расписание «X» и его чат» / «Чат и 2 расписания»).
   - Отмена — ничего не удаляется.
   - Крайние случаи: расписание без сессии — просто удаляется само; чат без расписания — обычное поведение; сработавшее расписание, создавшее себе новую сессию, тоже считается связанным.
   - По коду: связь уже есть в данных (`schedules.session_id`, `scheduler::open_session`), но удаление её не каскадит — `harness::delete_session` расписания не трогает, а удаление расписания не трогает сессию. Нужен каскад в обе стороны + обновлённые подтверждения в UI.

17) **Кнопка «Стоп» срабатывает через раз — во всех чатах: проекты, Harness, «Заметки и файлы».** Отправил сообщение — появилась «Стоп» (прервать ответ). Нажимаю: иногда останавливает, иногда нет, закономерность не видна. Механизм общий для всех трёх контекстов (`cancel_run` / `cancel_session_run` / `cancel_notes_run` ставят один и тот же флаг, а проверяется он в одном месте — `agent/loop.rs`), поэтому и причина, и починка общие.
   - Причина 1 (главная): флаг отмены проверяется только в начале шага — `agent/loop.rs`, `for step in 1..=config.max_steps { if run.is_cancelled(config) … }`. Всё, что длится внутри шага, отмену не замечает: потоковая генерация ответа (`call_llm`) и долгие инструменты (`bash` до 120 с, `ssh`, тяжёлые файловые операции). Отсюда «то работает, то нет»: попал в паузу между шагами — сработало, попал в середину стрима — нет.
   - Причина 2: после завершения прогона с причиной `cancelled` очередь сообщений сразу выплёвывается — `useChatRun.ts`, `flushQueue` («When a run finishes (done/error/cancelled), flush the queued messages»). Если в очереди было следующее сообщение, мгновенно стартует новый прогон, и выглядит это так, будто «Стоп» не сработал вообще.
   - Что нужно: проверять флаг во время стрима (на каждом чанке / раз в N мс) и реально закрывать HTTP-ответ, а не дожидаться конца шага; в долгих инструментах — тоже прерываться (SIGTERM процессу `bash`, таймаут на `ssh`).
   - После «Стоп» очередь не запускать автоматически: держать до явного действия пользователя (или спрашивать «отправить оставшееся?»).
   - UI: показывать «останавливаю…», пока бэкенд не подтвердил; `cancel_run`/`cancel_session_run`/`cancel_notes_run` возвращают `false`, если активного прогона нет — это состояние должно гасить кнопку, а не оставлять её «нажатой».
   - Решение: после «Стоп» очередь сохраняется и не запускается сама; показываем кнопку «Отправить оставшееся».
