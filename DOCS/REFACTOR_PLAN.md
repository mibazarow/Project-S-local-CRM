## 0. Цель и границы

**Цель:** сделать кодовую базу меньше, проще, предсказуемее и дешевле в поддержке. Убрать мёртвый код, развязать монолиты, выровнять границы слоёв, повысить надёжность и тестируемость — **без потери функционала и без редизайна**.

**Не входит:**
- новые фичи, изменения UX/дизайна, текстов, API-контрактов для пользователя;
- изменение поведения канбана, чатов, расписаний, агента;
- смена схемы БД «заодно» (только если срез явно про миграцию и с тестами);
- массовые обновления зависимостей;
- переписывание «с нуля» и big-bang;
- код на Windows/Linux.

**Definition of Done для каждого среза:**
- [ ] поведение не изменилось (существующие тесты + характеризационные тесты);
- [ ] `npm test`, `npm run build`, `cargo test` зелёные;
- [ ] нет новых предупреждений/ошибок линтеров;
- [ ] публичные IPC/структуры данных не сломаны;
- [ ] срез удалён из этого файла;
- [ ] изменения **не коммитятся**; финальный общий коммит — после всего рефакторинга (может сделать пользователь).

## 2. Принципы

- **Characterization first:** перед разбором монолита — тесты на текущее поведение; рефакторинг не должен менять наблюдаемое поведение.
- **Strangler, не big-bang:** выносим по одному модулю/ответственности, старый код удаляем только после переключения и зелёных тестов.
- **Слои и направление зависимостей:** UI/commands → сервисы → домен/репозитории → БД/платформа. Команды Tauri — тонкие адаптеры; БД и shell не должны жить в UI/агентских схемах.
- **Маленькие модули, но без дробления ради дробления:** цель — одна причина изменения на файл; 300–700 строк — ориентир, не догма.
- **Типизированные ошибки:** `Result` и доменные ошибки на границах; никаких строковых ошибок и `unwrap/expect` в production-путях. Массово не заменять: сначала аудит.
- **Явные контракты:** типы IPC/событий/БД — в одном месте; без `any` и дублирующихся DTO.
- **Один источник истины:** состояние чатов/задач/проектов не дублировать между store и компонентами; производные значения вычислять.
- **Безопасность по умолчанию:** argv вместо shell-строк, валидация путей, секреты вне plaintext, логи без секретов, CSP.
- **Измерять:** до/после — строки, warnings, размер бандла, время старта/тестов; не оптимизировать вслепую.
- **Платформенный шов:** `platform/` — единственное место для ОС-специфики; бизнес-логика не знает про macOS/Windows/Linux.

## 3. Очередь срезов

### R-01. Baseline и характеризационные тесты
**Зачем:** зафиксировать текущее поведение и метрики до изменений.
**Где:** `DOCS/REFACTOR_PLAN.md`, тесты, `scripts/`.
**Шаги:** записать текущие counts/warnings/bundle; добавить/уточнить smoke-тесты критических путей (проект → задача → чат → агент → расписание; заметки; поиск/индексация; онбординг; привязка расписания к пустому чату; `search_chats`/`open_chat`; лицензия; UI scale; фоновые чаты); зафиксировать команды проверки.
**Готово:** есть baseline-отчёт и тесты, которые ловят регрессии; production-код не менялся.

### R-15. Данные: N+1 и индексы (по замерам)
**Зачем:** скорость без изменения фич; точечно, только там, где замер покажет эффект.
**Где:** `projects/repo.rs` (`list_project_rows`/`db_row` — 3 запроса на проект), `scheduler/store.rs` (`schedules` по `related_task_id`/`session_id` в delete-каскаде).
**Шаги:** снять замеры списка проектов и delete-каскада; N+1 списка проектов свести к одному агрегатному запросу только если эквивалентность доказана тестами; индекс на `schedules(related_task_id)`/`schedules(session_id)` — только отдельной миграцией с тестами (схема в этом срезе не меняется).
**Готово:** замеры до/после; поведение не изменилось; если замер не показал эффекта — пункт закрывается без правок.

### R-16. Индекс/поиск: смена модели эмбеддингов
**Зачем:** смена модели с той же `dim` и тем же `backend = "ort"` не пересобирает векторы — в `file_vectors.backend` записан только backend, идентичности модели нет.
**Где:** `index/mod.rs` (`needs_reembed`, `update_vectors`), `embed/mod.rs` (`backend_id`), `file_vectors.backend`.
**Шаги:** решить, как отличать модели (id модели в `backend` без смены схемы либо реестр моделей); пересбор векторов при смене модели идёт по уже готовому пути смены backend/dim; тест «та же dim, другая модель → векторы заменены, дублей нет».
**Готово:** смена любой модели, а не только backend/dim, оставляет FTS и семантику согласованными; тесты.

### R-17. Производительность: старт, память, бандл (остаток)

### R-23. Секреты и безопасность
**Зачем:** API-ключи/MCP/SSH сейчас plaintext; CSP `null`; path/command validation.
