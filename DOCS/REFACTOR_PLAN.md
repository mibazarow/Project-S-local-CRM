## 0. Цель и границы

**Цель:** сделать кодовую базу меньше, проще, предсказуемее и дешевле в поддержке. Убрать мёртвый код, развязать монолиты, выровнять границы слоёв, повысить надёжность и тестируемость — **без потери функционала и без редизайна**.

**Не входит:**
- новые фичи, изменения UX/дизайна, текстов, API-контрактов для пользователя;
- изменение поведения канбана, чатов, расписаний, агента;
- смена схемы БД «заодно» (только если срез явно про миграцию и с тестами);
- массовые обновления зависимостей;
- переписывание «с нуля» и big-bang;
- код на Windows/Linux.

**Definition of Done для каждого среза:**
- [ ] поведение не изменилось (существующие тесты + характеризационные тесты);
- [ ] `npm test`, `npm run build`, `cargo test` зелёные;
- [ ] нет новых предупреждений/ошибок линтеров;
- [ ] публичные IPC/структуры данных не сломаны;
- [ ] срез удалён из этого файла;
- [ ] изменения **не коммитятся**; финальный общий коммит — после всего рефакторинга (может сделать пользователь).

## 2. Принципы

- **Characterization first:** перед разбором монолита — тесты на текущее поведение; рефакторинг не должен менять наблюдаемое поведение.
- **Strangler, не big-bang:** выносим по одному модулю/ответственности, старый код удаляем только после переключения и зелёных тестов.
- **Слои и направление зависимостей:** UI/commands → сервисы → домен/репозитории → БД/платформа. Команды Tauri — тонкие адаптеры; БД и shell не должны жить в UI/агентских схемах.
- **Маленькие модули, но без дробления ради дробления:** цель — одна причина изменения на файл; 300–700 строк — ориентир, не догма.
- **Типизированные ошибки:** `Result` и доменные ошибки на границах; никаких строковых ошибок и `unwrap/expect` в production-путях. Массово не заменять: сначала аудит.
- **Явные контракты:** типы IPC/событий/БД — в одном месте; без `any` и дублирующихся DTO.
- **Один источник истины:** состояние чатов/задач/проектов не дублировать между store и компонентами; производные значения вычислять.
- **Безопасность по умолчанию:** argv вместо shell-строк, валидация путей, секреты вне plaintext, логи без секретов, CSP.
- **Измерять:** до/после — строки, warnings, размер бандла, время старта/тестов; не оптимизировать вслепую.
- **Платформенный шов:** `platform/` — единственное место для ОС-специфики; бизнес-логика не знает про macOS/Windows/Linux.

## 3. Очередь срезов

### R-24. Отмена, таймауты, блокирующий I/O (остаток)
**Уже снято (2026-10-23, не переделывать):** единый токен отмены есть и проходит сквозь все пути — `AgentRegistry.cancels` → `AgentRunConfig.cancel` → `ToolCtx.cancel`; проверки: в LLM-стриме (`llm/streaming.rs::run_sse`), между шагами и между tool-вызовами раунда (`agent/loop.rs`, `agent/loop/step.rs`), в ожидании подтверждения (`chat/run/bridge.rs::ChannelConfirmer::await_decision`, поллинг 200 мс), в дочерних процессах (`bash` убивает child по флагу, `agent/ssh/session.rs::run_process` — так же, `osascript`/`open_with` — по таймауту). Флаг регистрируется до долгого старта run-потока (БД, конфиги, сборка контекста, компакция) и снимается по идентичности (`state.rs::clear_cancel`), поэтому «Стоп» не теряется ни в окне старта, ни между раундами, а поздний clear старого рана не роняет флаг нового. Таймауты: per-tool 240 с в `execute_with_timeout` (прерывается остановкой, а не дожидается лимита), watchdog `max_duration`/`stall_timeout`, LLM connect 15 с + read/inactivity 180 с, `bash` 120 с, `ssh` 10–1800 с, MCP per-server, `process_stop` TERM→KILL по группе процессов. Блокирующий I/O в async-командах обёрнут в `spawn_blocking` (все `async fn` в `commands/`), сам ран живёт на отдельном OS-потоке. Фоновая очередь сообщений не теряется: при отмене held, при старте нового рана — re-enqueue. Тесты: `confirmation_is_interrupted_by_a_stop_request`, `stop_while_a_tool_runs_does_not_wait_out_the_tool_timeout`, `a_late_clear_from_an_old_run_does_not_drop_the_new_run_flag`, `bash_cancel_kills_the_child_promptly`, `run_process_cancel_kills_the_child_promptly`, cancel/watchdog/timeout-тесты в `agent/loop/tests.rs`.
**Где остаток:** `agent/harness_tools/shell_tools.rs`, `platform/process.rs`, `llm/streaming.rs`.
**Остаток:** (1) `bash` убивает только прямого `sh`-ребёнка, не группу процессов: внуки (и два reader-потока, висящих на их stdout/stderr) переживают stop/timeout — нужен платформенный хелпер «foreground-команда в своей группе + сигнал группе» (unix `process_group(0)` + `kill -KILL -pgid`, Windows `taskkill /T /F`); это трогает платформенный шов, поэтому отдельным срезом. (2) «Стоп» при молчащем LLM-стриме замечается только на следующем чанке либо по 180 с read-таймауту сокета: прервать блокирующий `read_line` можно только читателем в отдельном потоке, новый механизм отмены сознательно не заводим. (3) `execute_with_timeout` отпускает detached-worker: инструмент, который не смотрит в `ctx.cancel`, может дописать побочный эффект уже после остановки рана (документированное ограничение синхронного харнеса).
**Готово:** остаток закрыт или явно помечен как не нужный; поведение stop/очереди не менялось.
