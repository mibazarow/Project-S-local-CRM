## 0. Цель и границы

**Цель:** сделать кодовую базу меньше, проще, предсказуемее и дешевле в поддержке. Убрать мёртвый код, развязать монолиты, выровнять границы слоёв, повысить надёжность и тестируемость — **без потери функционала и без редизайна**.

**Не входит:**
- новые фичи, изменения UX/дизайна, текстов, API-контрактов для пользователя;
- изменение поведения канбана, чатов, расписаний, агента;
- смена схемы БД «заодно» (только если срез явно про миграцию и с тестами);
- массовые обновления зависимостей;
- переписывание «с нуля» и big-bang;
- код на Windows/Linux.

**Definition of Done для каждого среза:**
- [ ] поведение не изменилось (существующие тесты + характеризационные тесты);
- [ ] `npm test`, `npm run build`, `cargo test` зелёные;
- [ ] нет новых предупреждений/ошибок линтеров;
- [ ] публичные IPC/структуры данных не сломаны;
- [ ] срез удалён из этого файла;
- [ ] коммит с осмысленным сообщением; изменения запушены.

## 2. Принципы

- **Characterization first:** перед разбором монолита — тесты на текущее поведение; рефакторинг не должен менять наблюдаемое поведение.
- **Strangler, не big-bang:** выносим по одному модулю/ответственности, старый код удаляем только после переключения и зелёных тестов.
- **Слои и направление зависимостей:** UI/commands → сервисы → домен/репозитории → БД/платформа. Команды Tauri — тонкие адаптеры; БД и shell не должны жить в UI/агентских схемах.
- **Маленькие модули, но без дробления ради дробления:** цель — одна причина изменения на файл; 300–700 строк — ориентир, не догма.
- **Типизированные ошибки:** `Result` и доменные ошибки на границах; никаких строковых ошибок и `unwrap/expect` в production-путях. Массово не заменять: сначала аудит.
- **Явные контракты:** типы IPC/событий/БД — в одном месте; без `any` и дублирующихся DTO.
- **Один источник истины:** состояние чатов/задач/проектов не дублировать между store и компонентами; производные значения вычислять.
- **Безопасность по умолчанию:** argv вместо shell-строк, валидация путей, секреты вне plaintext, логи без секретов, CSP.
- **Измерять:** до/после — строки, warnings, размер бандла, время старта/тестов; не оптимизировать вслепую.
- **Платформенный шов:** `platform/` — единственное место для ОС-специфики; бизнес-логика не знает про macOS/Windows/Linux.

2. R-05…R-12 — Rust-монолиты; можно параллелить только независимые модули, но не в одном рабочем дереве.
3. R-13 — платформенный шов (после стабилизации процессов/shell).
4. R-14…R-17 — данные/производительность (после разбиения доменов).
5. R-18…R-22 — фронтенд.
6. R-23…R-24 — безопасность/отмены.
7. R-25 — финал.

Каждый срез — отдельный PR/коммит. Не смешивать рефакторинг с фичами/дизайном. Если срез разрастается — дробить, а не «доделывать заодно».

## 5. Стоп-сигналы

- Тесты начали требовать изменения поведения — остановиться и пересмотреть срез.
- Появилась необходимость менять схему БД/публичный API — вынести в отдельный срез с миграцией.
- Срез тянет за собой пол-проекта — разрезать по границе модуля.
- «Заодно» захотелось поменять дизайн/тексты/фичи — это не сюда, это в `Q.md`.
- Появились новые warnings/упал bundle/тесты — не двигаться дальше.
