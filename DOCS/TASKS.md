# Канбан ↔ Список задач

**Статус:** черновик, не реализовано. Документ можно отдавать отдельной задачей на реализацию.
**Дата:** 2026-10-20.

> ## ⚠️ Жёсткое требование: канбан не ломать
>
> Всё, что уже работает в канбане, должно остаться **без изменений**:
> колонки и их фиксированная ширина 300 px, горизонтальный скролл, drag & drop,
> карточки, таймер, действия (агент/карандаш/комментарий/удалить), важность,
> чек-лист, подтверждения, фильтр «Просроченные», сортировка и порядок задач.
>
> Список — **отдельное представление** поверх тех же данных. Нельзя переделывать
> канбан «заодно», менять его разметку, CSS, поведение или контракты ради списка.
> Если для списка нужен общий код, его нужно выносить аккуратно, не меняя
> наблюдаемое поведение канбана, и покрывать регрессионными тестами.
>
> Любое изменение, которое меняет внешний вид или поведение канбана, считается
> ошибкой реализации этого ТЗ.

## 1. Идея

Добавить в раздел задач второе представление — **список**. Канбан и список показывают одни и те же задачи из одного источника данных; переключение вида не создаёт и не копирует задачи.

Список нужен, чтобы одним взглядом понимать:

- какие задачи сейчас в работе и сколько идёт таймер;
- какие задачи новые / не начаты;
- какие просрочены;
- какие важные;
- сколько сделано в чек-листе;
- сколько времени уже потрачено.

Пользователь должен переключаться между «Канбан» и «Список» в один клик, а создание задачи в любом виде сразу отражаться в обоих.

## 2. Текущее состояние

- В канбане три фиксированных backend-статуса: `new`, `progress`, `done`.
- Подписи колонок могут переименовываться на проект через `project.taskColumns`; дефолт — «Новые», «В работе», «Готово».
- Задача в `progress` с `startedAt != null` считается идущей: таймер тикает каждую секунду, `spentMs` — накопленное время.
- Отдельного статуса «Пауза» сейчас нет. Если таймер остановлен, задача, как правило, не находится в `progress` с активным `startedAt`. Это важно для группировки списка (см. открытые вопросы).
- В шапке задач уже есть фильтр «Просроченные» и переключатель «Файлы / Задачи».
- Поиск из UI удалён; фильтр по названию не возвращаем.
- Колонки канбана фиксированы по 300 px и скроллятся горизонтально. Список должен занимать всю доступную ширину средней панели.

## 3. UX

### 3.1. Переключатель вида

- В шапке задач, рядом с «Просроченные», сегментный переключатель:
  - `Канбан` (иконка колонок);
  - `Список` (иконка строк/списка).
- Стиль — как у существующих сегментных контролов приложения.
- Переключатель виден только на вкладке «Задачи»; на «Файлах» его нет.
- Выбранный вид сохраняется между запусками.
- Фильтр «Просроченные» и выбранный проект при переключении не сбрасываются.

### 3.2. Структура списка

Рекомендуемый вариант — **умная лента с группами**, а не плоская таблица.

Сверху — блок **«Сейчас»**:

- все задачи в `progress` с активным таймером;
- крупная строка с названием, живым таймером и кнопками «Пауза» / «Готово»;
- если таких задач нет — блок скрыт.

Ниже — группы:

1. **Просрочено** — задачи с `overdue = true` (могут быть из любого статуса).
2. **В работе** — `progress`, но без активного таймера (если такое состояние появится/существует).
3. **Новые** — `new`.
4. **Готово** — `done`, по умолчанию свёрнута.

Альтернатива: плоский список с сортировкой «сначала активные → просрочка → важные → дедлайн → остальные». Группы человекочитаемее, плоский список компактнее. Решение — в открытых вопросах.

Внутри группы сортировка по умолчанию:

1. важные;
2. ближайший дедлайн (просроченные — выше);
3. ручной `position`;
4. `id`.

Заголовок группы показывает количество задач. Группу можно свернуть; состояние свёрнутости запоминается на сессию.

### 3.3. Строка задачи

Одна строка — компактная, но информативная:

```
●  Переписать каталог                    01.10  ⚑  чек 2/5  01:24:10  ⏸ ✓ ✎ 💬 🗑
```

Слева направо:

- **статусная точка/пилюля** с цветом;
- **название** (до двух строк, дальше ellipsis);
- **важный** — красная левая полоска или флажок;
- **дедлайн** — дата/время; просроченный — красный;
- **чек-лист** — `2/5` и мини-прогресс (если чек-лист есть);
- **время** — затрачено всего; у активной задачи дополнительно текущая сессия;
- **действия** — играть/пауза, готово, карандаш, комментарий, удалить.

Для активной строки:

- лёгкий акцентный фон;
- пульсирующая точка;
- таймер обновляется раз в секунду;
- действия видны всегда или на hover (решить при реализации).

Для `done`:

- приглушённый текст;
- зачёркнутое название;
- без пульсации и без активного таймера.

Для просроченной:

- красная дата и, возможно, красная точка;
- если задача ещё и важная — красная рамка/полоска сохраняется.

### 3.4. Статусы и цвета

Использовать существующую палитру (`--accent`, `--danger`, `--ok`, `--text-muted`).

- `new` — нейтральный/серый.
- `progress` — акцентный синий/зелёный, живой таймер.
- `done` — зелёный/приглушённый.
- Просрочка — красный.
- Важная — красная рамка/полоска, как в карточке.
- «Пауза» — если появится отдельное состояние: янтарный.

Подписи статусов брать из `project.taskColumns`, а не хардкодить, чтобы переименование колонок работало и в списке.

### 3.5. Таймер

- Для активной задачи (`status === "progress" && startedAt != null`):
  - текущая сессия: `now - startedAt`;
  - всего: `spentMs + сессия`;
  - обновление раз в секунду, только для активных строк.
- Для остальных — только `spentMs`.
- Формат: `чч:мм:сс` или `чч:мм` для больших значений; существующий `formatSpent` переиспользовать.
- Не тикать весь список каждую секунду: таймер живёт в компоненте строки/активной строки.

### 3.6. Чек-лист

- В строке показывать `готово/всего` и тонкий прогресс-бар.
- Если чек-листа нет — блок не показывать.
- Пункты чек-листа в списке не раскрывать; отметка — в полном редакторе.
- В раскрытой строке — тот же редактор чек-листа, что в карточке.

### 3.7. Действия

Те же, что в карточке:

- обсудить с агентом;
- редактировать (полный редактор);
- комментарий;
- удалить (через общую модалку подтверждения).

Плюс действия, специфичные для списка:

- начать/продолжить;
- пауза (если состояние поддержано);
- готово;
- возможно, «показать в канбане» / «перейти к задаче» — не обязательно.

Все действия должны работать и в канбане, и в списке, без дублирования логики: вынести общие обработчики.

### 3.8. Редактирование

Рекомендуемый вариант — **раскрытие строки вниз**:

- клик по строке (или по карандашу) разворачивает под ней тот же `TaskEditor`, что используется в карточке;
- одновременно раскрыта максимум одна задача;
- сохранение/отмена — как в карточке;
- после сохранения строка обновляется, группа/сортировка пересчитываются.

Альтернатива — боковая панель/модалка; она сильнее отрывает от списка. Решение — в открытых вопросах.

### 3.9. Создание задачи

- В канбане «+» в колонке создаёт задачу с этим статусом (как сейчас).
- В списке:
  - общий «+» в шапке списка с выбором статуса; или
  - «+» в заголовке каждой группы.
- По умолчанию в списке создавать в `new` («Новые»).
- После создания задача сразу появляется в обоих представлениях; отдельного «перелёта» не требуется.
- Вопрос: нужно ли автоматически переключать вид после создания (см. открытые вопросы).

### 3.10. Drag & drop

Рекомендуется поддержать в списке:

- перетаскивание строки между группами = смена статуса;
- перетаскивание внутри группы = изменение `position`;
- визуальная линия вставки и подсветка группы;
- отмена/ошибка API возвращает строку на место.

Если drag & drop в списке окажется лишним, можно оставить только кнопки статуса; в канбане drag & drop остаётся.

### 3.11. Фильтры

- «Просроченные» работает в обоих видах.
- Фильтр не должен менять данные, только отображение.
- При включённом фильтре пустые группы скрывать, но показывать общий empty-state.
- Поиск по названию не возвращаем (удалён из продукта).

### 3.12. Пустые состояния

- Нет задач вообще: «Пока нет задач» + кнопка «Создать».
- Нет задач в группе: группу не показывать (или показывать свёрнутой).
- Всё готово: показать «Все задачи выполнены» и свёрнутую группу «Готово».
- Нет задач по фильтру: «Нет просроченных задач».

### 3.13. Анимации

- Переключение вида — без резкого скачка; сохранять позицию скролла по возможности.
- Раскрытие редактора — плавное.
- Пульсация активной строки — мягкая, с `prefers-reduced-motion`.
- Перетаскивание — линия вставки, без «прыжков».

### 3.14. Доступность и клавиатура

- Строка — фокусируемый элемент; Enter/Space открывает редактор.
- Кнопки действий — с `aria-label`/`title` на русском.
- Статус и просрочка — не только цветом, но и текстом/иконкой.
- Таймер не должен быть `aria-live` каждую секунду (чтобы не спамить скринридер).
- `prefers-reduced-motion` отключает пульсацию.

### 3.15. Адаптивность

- Список занимает всю ширину средней панели.
- На узкой ширине скрывать второстепенные колонки (чек-лист, время) или переносить их на вторую строку.
- Название не должно ломать layout: 2 строки + ellipsis.
- Канбан остаётся с фиксированными 300 px и горизонтальным скроллом.

## 4. Данные и состояние

- Новых полей в БД не требуется: используются `TaskDto` (`status`, `position`, `dueDate`, `dueTime`, `isPriority`, `checklist`, `overdue`, `spentMs`, `startedAt`).
- Группировка/сортировка — вычисляемые на клиенте.
- Выбранный вид — UI-настройка:
  - ключ вида `localStorage` (например, `project-s.tasks.view.<projectId>`) или глобальный;
  - fallback — «Канбан».
- Свёрнутость групп — состояние сессии (не обязательно сохранять навсегда).
- Раскрытая задача — состояние вида; при переключении проекта сбрасывается.
- Все изменения (статус, позиция, таймер) идут через существующие IPC-команды; список не вводит новых API.
- Оптимистичные обновления: строка сразу меняет статус/позицию, при ошибке — откат и сообщение.
- Таймер активной строки обновляется локально, без запроса к бэкенду каждую секунду.

## 5. Крайние случаи

- Несколько задач одновременно в `progress` — блок «Сейчас» показывает все.
- Задача одновременно просроченная и важная — красная дата + красная рамка/полоска.
- Пустой чек-лист — блок не рендерится.
- Очень длинное название — 2 строки + ellipsis; полный текст в редакторе/подсказке.
- Нет задач / все готовы / только просроченные — соответствующие empty-state.
- Переименование колонок в проекте — подписи в списке обновляются.
- Переключение проекта — вид и фильтр не должны применяться к чужому проекту; раскрытая задача сбрасывается.
- Задача удалена/изменена агентом или в другом виде — список обновляется по существующим событиям.
- Задача создана в канбане, когда открыт список — появляется в списке без перезагрузки.
- Задача создана в списке — появляется в канбане.
- Фильтр «Просроченные» + drag & drop: перетаскивание не должно терять задачу из фильтра или ломать порядок.
- Задача в архиве проекта — раздел задач скрыт, список недоступен.

## 6. Рекомендуемые дефолты

- Группы по статусам + блок «Сейчас».
- Раскрытие строки вниз с полным редактором.
- Общий «+» в шапке списка с выбором статуса; по умолчанию `new`.
- Активная строка показывает текущую сессию + всего; остальные — только всего.
- Drag & drop между группами и внутри группы.
- Вид запоминается **на проект**.
- После создания вид не переключается автоматически; задача просто появляется в обоих видах. Если пользователь хочет автоматический переход — это отдельная настройка/решение.

## 7. Открытые вопросы

1. **Автопереключение после создания**: если задача создана в канбане, переключаться ли принудительно в список? Или наоборот? Или просто оставлять текущий вид?
2. **Структура**: группы по статусам или плоская лента с умной сортировкой?
3. **Редактирование**: раскрытие строки вниз или боковая панель/модалка?
4. **Создание в списке**: один общий «+» с выбором статуса или отдельный «+» в каждой группе?
5. **Таймер**: показывать только общее затраченное время или для активной задачи отдельно текущую сессию + всего?
6. **Drag & drop в списке**: нужен ли он вообще, или достаточно кнопок смены статуса?
7. **Запоминание вида**: на проект или глобально для всех проектов?
8. **«Пауза»**: вводить ли отдельный статус `paused` (потребует изменений backend/БД), или считать «паузой» любую задачу не в `progress`? Сейчас отдельного состояния нет.

## 8. План реализации

1. **Каркас:** переключатель вида, сохранение выбора, пустой список, группировка по статусам, read-only строки.
2. **Строка:** статус, важность, дедлайн, чек-лист, время, live-таймер, empty-states.
3. **Действия:** начать/пауза/готово, полный редактор в раскрытии, комментарий, удаление через общую модалку.
4. **Создание:** «+» в списке, выбор статуса, синхронизация с канбаном.
5. **Drag & drop:** между группами и внутри, откат при ошибке.
6. **Полировка:** адаптивность, доступность, анимации, тесты, сохранение скролла/вида.

## 9. Критерии готовности

- Переключатель «Канбан / Список» работает и запоминается.
- Список показывает те же задачи, что канбан, с корректными статусами, важностью, дедлайнами, чек-листом и временем.
- Активная задача показывает живой таймер; пауза/готово работают.
- Создание в любом виде сразу видно в обоих.
- Редактирование из списка открывает тот же полный редактор.
- Фильтр «Просроченные» работает в обоих видах.
- **Канбан не изменился:** колонки 300 px и горизонтальный скролл, drag & drop, карточки, таймер, действия, важность, чек-лист, фильтр и подтверждения — поведение и внешний вид прежние.
- Нет регрессий в канбане, таймере, drag & drop, удалении и подтверждениях.
- Пустые состояния и узкая ширина выглядят аккуратно.

## 10. Тесты

- Группировка/сортировка: статусы, просрочка, важность, дедлайн, `position`.
- Переключение вида и сохранение выбора.
- Строка: live-таймер, формат времени, чек-лист, важность, просрочка, `done`.
- Действия: старт/пауза/готово, редактирование, удаление с подтверждением.
- Создание в списке и канбане, появление в обоих видах.
- Drag & drop: смена статуса/позиции, откат при ошибке.
- Фильтр «Просроченные» в обоих видах.
- Доступность: роли, фокус, подписи, reduced motion.
- Отсутствие лишних запросов/рендеров при тикающем таймере.
- **Регрессия канбана:** весь существующий набор тестов канбана и карточек проходит без изменений; переключение в список и обратно не меняет DOM/поведение канбана.

## 11. Вне рамок

- Новый backend/API для вида (кроме возможного `paused`, если решим его вводить).
- Возврат поиска по задачам.
- Изменение модели задач, канбана или таймера.
- Любое изменение поведения или внешнего вида канбана ради списка.
- Синхронизация с внешними трекерами.
