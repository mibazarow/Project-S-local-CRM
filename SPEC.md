# Project S — техническое задание (v1)

Локальная десктопная CRM-система с встроенным ИИ-агентом и агентским харнесом. Один пользователь. Всё работает на машине пользователя, LLM — через OpenAI-совместимый API.

Статус: ТЗ v1, подтверждено владельцем. Дата: 2026-10-16.

---

## 1. Концепция

Project S — это личная система учёта проектов и клиентов, где ядром является файловая структура («одна папка = один проект»), а ИИ-агент встроён в каждый экран: ищет по файлам, ведёт задачи, работает с доступами. Дополнительно приложение содержит «Харнес» — полноправного ИИ-агента с доступом ко всему компьютеру (файлы, терминал, браузер, планировщик), аналогичного современным coding-агентам (Kilo/Claude Code), но внутри нашего приложения.

Три вкладки были в первоначальном замысле, в v1 остаются **две**:

| Вкладка | Назначение |
|---|---|
| **Проекты** | CRM-часть: клиенты/проекты, файлы, задачи, поиск, чат-агент per-проект |
| **Харнес** | Универсальный агент с полным доступом к компьютеру, сессии, расписания, память |

Третья вкладка «Чат» (болталка без CRM-контекста) **из ТЗ исключена**: поболтать можно с харнес-агентом.

### Не является проектом (anti-goals)

- Не командная CRM: никаких ролей, многопользовательского доступа, синхронизации между машинами.
- Не веб-сервис: приложение локальное, серверной облачной части нет.
- Не воронка продаж: это учёт проектов (договоры, счета, доступы, документы), pipeline этапов в v1 нет.
- Не таск-трекер общего назначения: задачи привязаны к проекту.

## 2. Платформа и стек

| Слой | Технология |
|---|---|
| Оболочка | **Tauri 2** (macOS в v1; архитектура кроссплатформенная — Windows/Linux потенциально без переделки ядра) |
| Бэкенд | **Rust**: агент-луп, файловые операции, индексация, SQLite, эмбендинги, CDP-браузер, планировщик |
| Фронтенд | **React + TypeScript + Vite** |
| Стили | **Обычный (vanilla) CSS** — без Tailwind и аналогичных утилитарных фреймворков. Обычный CSS/модули CSS для максимальной гибкости дизайна |
| База данных | **SQLite** (одна база в рабочей директории): метаданные, задачи, чаты, полнотекстовый индекс, векторный индекс, память агента, расписания |
| Векторный поиск | sqlite-vec (или эквивалентный векторный индекс в SQLite) + FTS5 |
| Эмбендинги | **EmbeddingGemma 2** (`google/embeddinggemma-2`, Apache 2.0): мультимодальная (текст+код, картинки, видео, аудио → единое 768-d пространство), 740M параметров, селективная загрузка энкодеров: в Project S — текст (270M) + vision (170M) ≈ 440M, аудио/видео вне v1. Инференс — **ONNX Runtime in-process через Rust-crate `ort`** (CPU), без llama.cpp и без Python-микросервисов. ONNX-веса в релизной сборке — офлайн из коробки; инференс в fp32/bf16 (float16 запрещён — даёт NaN). Пайплайн переносится с обкатанного `bitrix-smart-consultant`: task-префиксы (`task: search result | query:` / `title: {title} | text: {content}`), mean-pooling + L2-нормализация, MRL 768→512/256 с ренормализацией после усечения, два вектора на файл (текст + имя, вес имени 0.3), инкрементальный ребилд по хэшу текста |
| Извлечение текста | Локальные Rust-парсеры: PDF (pdf-extract/lopdf), DOCX/XLSX/PPTX (zip+xml), md/txt как есть. OCR — вне v1 |
| LLM | Любой **OpenAI-совместимый** endpoint (`/chat/completions` + tool calling). Пользователь сам подключает: облако, прокси, Ollama и т.п. |
| Агентный луп | **Свой на Rust** (запрос → tool calls → ответ → цикл), без внешних агентных фреймворков |
| Никакого Python | В проекте Python не используется нигде: весь бэкенд, инструменты агента и заимствованные механики (см. 6.4) — только Rust. ONNX Runtime бандлится как нативная C-библиотека (crate `ort`), не как Python |
| Браузер для харнеса | Rust-мост к установленному Chrome/Chromium через **CDP** (headless и headful) |
| UI-язык | Только русский, без i18n-слоя в v1 |
| Визуальный стиль | **Светлая тема в стиле macOS**: системный шрифт (SF Pro), unified-тулбар, сегментные контролы (NSSegmentedControl), Finder-подобное выделение в списках, hairline-бордеры, нативные switch/toggle. Тулбар — тёмный (#182533), акцент — приглушённый синий **#376A9F** (кнопки, чаты, выделение, фокус). Приложение должно выглядеть консистемно с macOS |
| Иконка приложения | Готовый макет — `ico.png` в корне проекта: тёмный фон #182533, белая рукописная «S», красная точка (#FA6269). Для сборки Tauri перегенерировать из неё полный набор `.icns`/PNG-размеров (16–1024) |

## 3. Модель данных и хранения

### 3.1 Рабочая директория

- При первом запуске (онбординг) приложение спрашивает, где хранить данные. Дефолт: `~/Documents/PROJECT-S`.
- В выбранном месте автоматически создаётся каркас из **трёх папок верхнего уровня**: `Projects/`, `Harness/`, `Settings/` — порядок важнее экономии вложенности, бардак на верхнем уровне запрещён.
- Файлы проектов — обычные папки, их можно трогать руками в Finder.

```
PROJECT-S/
├── Projects/                # все CRM-проекты
│   └── <имя проекта>/       # одна подпапка = один проект
│       ├── datas.md         # создаётся автоматически: доступы, пароли, «пароли и явки»
│       ├── tasks/           # экспорт задач (md), источник истины — SQLite
│       ├── Входящие/        # вложения из чатов (создаётся автоматически)
│       ├── INBOX.md         # журнал входящих вложений (авто-записи)
│       └── ...              # любые подпапки: Документы/, Брендбук/, подпроекты и т.д.
├── Harness/                 # рабочая территория агента-харнеса по умолчанию (изначально пуста)
│   └── tmp/                 # временная зона харнеса: промежуточные файлы, артефакты, скачивания
└── Settings/                # всё приложение: настройки, данные, ресурсы — только здесь
    ├── config/              # plaintext-конфиги (см. 3.4): llm.json, app.json, indexing.json, mcp.json
    ├── skills/              # скиллы агентов (см. 6.2): встроенные + пользовательские
    ├── .db/                 # SQLite: чаты, задачи, память, FTS/векторные индексы (скрытая, см. принцип ниже)
    ├── logs/                # журнал запусков и tool-calls
    └── backups/             # архивы бэкапов (по кнопке)
```

- `Harness/` — дефолтный каталог операций харнеса (запись файлов, скрипты, временные артефакты), если пользователь явно не укажет другой путь. Харнес при этом может работать по всему компьютеру (с подтверждениями, см. 5.2).
- Внутри `Settings/` — фиксированная структура, новые типы файлов кладутся только в соответствующую подпапку; приложение не создаёт файлов в корне рабочей директории.
- **Принцип открытости (однопользовательское приложение)**: ничего не скрываем от владельца. Никаких hidden-файлов и dot-папок, **единственное исключение — `Settings/.db/`** (SQLite). Всё остальное видно в Finder. Пользователь может в любой момент залезть и править файлы руками (проекты, конфиги, скиллы) — приложение всё подхватывает через watcher и перечитывание, конфликтов «только через UI» нет.
- **БД — исключение**: в `Settings/.db/` руками не лезем (SQLite WAL — легко повредить); изменение данных в БД — только через приложение/агента. Для «починить руками» — экспорт/импорт через UI (в «Будущем»).

### 3.2 Проекты и клиенты

- **Проект — приоритетная сущность.** Создаётся кнопкой «+» с именем (домен сайта или произвольный текст) → автоматически создаётся папка, `datas.md`, `tasks/`.
- **Клиент отдельной сущностью не заводится**: пользователь идентифицирует клиента по проекту. Если у клиента несколько проектов/подпроектов — пользователь раскладывает их подпапками внутри проекта.
- В БД проект имеет запись (имя, путь, даты), но источник истины по файлам — файловая система.

### 3.3 Что хранит SQLite

- Проекты и связи; задачи (source of truth) с экспортом в `tasks/*.md` (YAML-frontmatter: статус, проект, даты, теги);
- Чаты: **один непрерывный чат на проект** (история сообщений, tool-calls, суммаризации); сессии харнеса;
- Индекс: таблицы FTS5 + вектора эмбендингов по файлам проекта;
- Память харнес-агента (глобальная, см. 6.3); расписания; журнал запусков.

### 3.4 Конфигурация

- Директория `Settings/config/` с plaintext-файлами в формате **JSON** (разделение: `llm.json`, `app.json`, `indexing.json`, `mcp.json` — подключения к MCP-серверам, см. 6.2).
- Управляются через UI настроек, но **могут правиться руками** — приложение перечитывает изменения (hot reload через watcher).
- **API-ключ хранится в конфиге в plaintext** (осознанное решение владельца: переносимость папкой важнее; шифрование — в «Будущем»).

### 3.5 datas.md

- Открытый Markdown в папке проекта (без шифрования в v1) — как текущая практика `DATAS_*.txt`.
- Индексируется наравне с другими файлами: ИИ находит доступы по запросу («найди доступы к серверу»).
- SSH-профили: каноническая секция `## SSH <имя>` со строками `host:`/`user:`/`port:`/`password:`/`key:`; парсер также принимает рукописные секции — любой непустой заголовок `## <title>` (имя профиля = заголовок), маркированные строки (`- Хост: …`) и русские метки (`Хост:`, `Пользователь:`, `Порт:`, `Пароль:`, `Ключ:`); секция без host+user игнорируется. Пароли из datas.md никогда не возвращаются инструментами (только `hasPassword`/`auth`).

### 3.6 Бэкап

- Кнопка «Резервная копия»: SQLite + копия `Projects/` → один архив `.zip` с датой в выбранное место (по умолчанию `Settings/backups/`).
- Папки обычные → Time Machine подхватывает без усилий приложения.

## 4. Вкладка «Проекты»

### 4.1 Экран

- Слева — список проектов (карточка: имя, кол-во файлов/задач, дата открытия). По клику — проект: дерево файлов + справа чат-агент проекта.
- **Кнопка создания проекта (Q-21):** в шапке сайдбара проектов контрол создания — акцентная кнопка с круглым белым плюсом и видимой подписью **«Новый проект»** (плюс остаётся круглым акцентным, подпись — слева от него в цвет акцента). Обработчик, inline-поле ввода имени, порядок контролов и поведение создания не меняются; подпись не должна ломать шапку сайдбара.
- **Индикатор активных задач:** на карточке проекта в списке слева — маленькая ненавязчивая иконка Play (в тон интерфейса, подсказка «Есть задачи в работе», доступная метка у иконки), если в проекте есть хотя бы одна задача в статусе «В работе» (`progress`). Сигнал — существующий признак наличия задачи в `progress` (без нового «тикающего» источника): бэкенд отдаёт булево `hasActiveTasks` в DTO списка проектов, вычисляя его тем же запросом (`EXISTS(SELECT 1 FROM tasks WHERE project_id = … AND status = 'progress')`), без отдельного вызова на проект. Иконка не сдвигает вёрстку, когда её нет; список проектов обновляется по существующему событию `tasks-changed` (смена статуса задачи).
- **Размер окна:** минимальное — 1000×600 px (в Tauri — `minWidth: 1000`, `minHeight: 600`), дальше растягивается без ограничения. Панель чата на экране проекта широкая (~450 px), центральная колонка сжимается первой.
- Никакого дашборда с метриками в v1.

### 4.2 Файловый менеджер (псевдо)

- Дерево файлов проекта; создание проектов/папок, drag&drop файлов в дерево, удаление.
- Операции над файлами/папками как в обычной файловой системе (hover-действия: переименовать, дублировать, удалить; переименование — inline-поле, по умолчанию выделена только основа имени без расширения — расширение сохраняется, пока пользователь сам явно его не выделит и не изменит; у папок выделяется имя целиком).
- md/txt — просмотр и редактирование Markdown прямо в правой панели в двух режимах как в VS Code: view (отрендеренный md) / edit (исходник в моноширинном поле), переключение кнопкой «Редактировать» ↔ «Готово» (сохраняет и рендерит заново).
- docx/pdf/картинки и прочее — открытие внешним редактором/просмотрщиком по двойному клику; картинки — встроенный предпросмотр. PDF-вьювер внутри приложения — вне v1.
- Проект можно переименовать (карандаш в списке проектов, inline-поле) — переименовывается и папка, и запись в БД.
- **Режим файлов на проект (список/сетка):** переключатель «Список/Сетка» помнится **отдельно для каждого проекта** и хранится **в БД проекта**: колонка `projects.files_view` (`TEXT NOT NULL DEFAULT 'list'`, `CHECK (files_view IN ('list','grid'))`, миграция v34). DTO проекта отдаёт `filesView`. Переключение сохраняет значение сразу (команда `project_set_files_view`; неизвестное значение нормализуется в дефолт `list`) и рассылает `projects-changed`, поэтому список проектов в сторе обновляется. `FilesPanel` инициализирует режим значением проекта: при переключении между проектами каждый сохраняет свой режим (без сброса в «список»), режим помнится и после перезапуска приложения. Разметка и классы общего сегментного контрола (ViewToggle/Segmented) не меняются.
- **Перенос файлов между папками (режим списка):** в режиме списка файл можно перетащить указателем в другую папку — тот же механизм, что у заметок/проектов/канбана (`usePointerDrag`, HTML5 DnD в WKWebView ненадёжен): призрак строки наклонён на 4° и «поднят» с тенью (`.drag-ghost`), строка следует за курсором, исходная строка приглушена (`.dragging`). Драг начинается со строк **файлов и папок**; цели дропа — строки папок (`data-drop-dir`) и корень дерева (корень проекта, `data-drop-dir=""`): допустимая цель подсвечивается (`.drop-over`), недопустимая — нет; перенос в текущую папку-родителя — no-op. Дроп выполняет перемещение существующей командой `fs_move`, после чего дерево и предпросмотр обновляются по `fs-changed`, а выделение следует за новым путём. Esc и `pointercancel` отменяют перетаскивание; клик после драга не выделяет и не открывает строку. Клик-предпросмотр, двойной клик, контекстное меню и inline-переименование сохраняются. В режиме «сетка» перетаскивание остаётся HTML5 DnD (плитки уже допускают перенос папок в папки и корень).
- **Drag-and-drop из Finder в проект (копирование):** из Finder в проект можно перетащить **любой файл или папку** — на строку/плитку папки (`data-drop-dir`) или в корень дерева/сетки (`data-drop-dir=""`): цель подсвечивается (`.drop-over`), недопустимая цель — нет. Дроп **копирует** файлы (источник остаётся в Finder, перемещения нет); папки копируются рекурсивно с сохранением структуры, коллизия имён разрешается существующим суффиксом `unique_name` (« copy» / « copy N»). Пути и позиция курсора приходят из Tauri-канала drag-drop событий вебвью (`useOsFileDrag`): HTML5 DnD в WKWebView не передаёт реальные пути; дроп поверх области вложений чата (`data-chat-drop`) обрабатывает чат, дерево/сетка его игнорируют. Бэкенд `fs_import` отклоняет относительные пути источников, импорт папки в саму себя/свою подпапку и некорректную цель (несуществующая/не-папка) — ошибка показывается в существующем стиле (`.tree-error`); после импорта дерево обновляется по `fs-changed`, watcher индексирует скопированные файлы.
- **Drag-and-drop из Finder в «Заметки и файлы» (копирование):** те же семантика и подсветка целей, что у проектов: дроп файла/папки из Finder на строку папки заметок (`data-drop-dir`) или на корень дерева (`data-drop-dir=""`) **копирует** их в хранилище `Notes/` (источник остаётся на месте, папки — рекурсивно с сохранением структуры, коллизии — суффикс « copy» / « copy N»). Новая команда `notes_import` (dest — папка хранилища или корень) использует общий с проектами механизм импорта и общий path-policy: относительные пути источников, импорт хранилища в самого себя, выходы за пределы (`..`, абсолютные цели) и symlink-цели отклоняются, ошибка — в существующем стиле (`.tree-error`). После импорта дерево заметок обновляется по `notes-changed`, watcher переиндексирует скопированные файлы; отдельных строк БД для файлов заметок нет (как и раньше — только индекс).
- **«Заметки и файлы: хранение любых файлов» (Q-14):** раздел (третья вкладка, хранилище `Notes/`) хранит **не только `.md`** — картинки, PDF, архивы, текстовые и любые другие файлы; раздел называется **«Заметки и файлы»** во всех UI-подписях (вкладка тулбара, палитра команд, заголовок сайдбара, пустые состояния, настройки импорта); внутренние идентификаторы (`notes_*`, вкладка `notes`) не меняются. Дерево показывает файлы и папки с корректными иконками и тегами расширения (общий `EntryIcon`). Предпросмотр выбранного файла в центральной панели: **`.md`** — прежний блочный редактор с автосохранением (поведение не меняется); **текст/код** (`is_text`) — чтение через `notes_read` (уже работает для любого текста), показ **только для чтения**; **картинки** — inline `<img>`; **PDF** — встроенный просмотр (iframe с blob-URL из data URL, как в панели файлов проекта, лимит 25 МБ); **прочие типы** — карточка: иконка, имя, размер/тип и кнопка **«Открыть в системе»** (существующий `open_with` со scope `notes`). Чтение бинарных файлов для предпросмотра — узкая команда `notes_read_binary_data_url(rel, maxBytes)`: общий с проектами механизм (`fs_ops` data URL: картинки до `maxBytes`, PDF до 25 МБ с проверкой магии `%PDF-`, прочие — ошибка), пути — та же политика хранилища заметок (`contain_existing`: `..`, абсолютные пути и symlink-выходы за пределы `Notes/` отклоняются). `notes_create` и создание новых заметок по-прежнему создают `.md`; редактирование не-`.md` файлов не требуется.
- **Заметки из шаблона убраны (Q-15):** создание заметки из шаблона не используется, шаблоны заметок не нужны. На тулбаре раздела «Заметки и файлы» остались только «Новая заметка» и «Новая папка» — оба создают обычный `.md`/папку через `notes_create`; селект «Из шаблона…», состояние шаблонов заметок, обёртка `templateCreateNote` и команда `template_create_note` удалены. Шаблоны проектов/задач/документов (`template_create_project`, `template_create_task`, `template_document`) не затронуты.
- **Интернет и Vision для агента заметок (Q-17):** агент раздела «Заметки и файлы» (чат заметок) получает три инструмента помимо своих заметочных: **`websearch`** и **`webfetch`** — те же самые инструменты харнеса (`net_tools`), с теми же именами и схемами (переиспользование, не форк), read-only, без подтверждений; и **`vision`** — анализ изображения из хранилища `Notes/` через **настроенного провайдера/модель** (`relPath` — путь внутри хранилища по той же политике `contain_existing`, `prompt` — что искать). `vision` читает картинку в data URL и отправляет её в `chat/completions` текущей модели; если vision-модель не настроена/не поддерживается (`vision_enabled()` = false), инструмент возвращает **понятную ошибку**, а не молча игнорирует картинку. Полноценный **CDP-браузер, bash/терминал и прочие shell-инструменты заметкам не выдаются** — каталог агента заметок остаётся заметочно-сетевым; каталоги проекта и харнеса от этого не меняются.
- **Ссылки на заметки из ответов агента (Q-16):** клик по ссылке на заметку в ответе агента (чат проекта, харнес, чат заметок) открывает заметку **внутри раздела «Заметки и файлы»**, а не во внешнем редакторе/браузере. Консервативный резолвер (`resolveNoteLink`) считает заметочной ссылкой только: явные `note:`/`notes:` (схема снимается, остаток — vault-относительный путь), относительные пути с расширением `.md`/`.markdown` (без сегментов `..`) и абсолютные пути внутрь хранилища (с сегментом `/Notes/` — берётся часть после него). Все прочие ссылки (`http(s)`, `mailto`, `tel`, иные схемы, не-`.md` файлы, картинки, полуссылки `#…`) сохраняют прежнее поведение: клик не перехватывается, внешние открываются как раньше. Для заметочных ссылок клик делает `preventDefault` (внешнее открытие не происходит) и выполняет существующий переход `requestNote(relPath)` + переключение на вкладку `notes`; выбор заметки — прежний резолв `pendingNotePath` в `NotesView` через `resolveEntry`/`notesList` (новых IPC-команд нет). Если заметка не найдена — показывается ошибка в существующем тост-стиле (`toast("err", …)`), внешнее открытие не выполняется. Обработчик клика живёт в `MarkdownMessage` (делегирование по `<a>` внутри тела сообщения), регистрация обработчика — в `App` (вызывает `requestNote` + `setTab("notes")`). Схема `note:`/`notes:` пропускается через DOMPurify (`ALLOWED_URI_REGEXP`), иначе sanitizier снимает `href`.
- **Подпапки и перенос папок (режим списка):** кнопка «Новая папка» на тулбаре панели файлов создаёт подпапку в выделенной папке (если папка не выделена — в корне проекта), а пункт «Новая папка» в контекстном меню папки — подпапку именно в этой папке: имя вводится в inline-поле (`RenameInput`), некорректное и дублирующее имя отклоняет существующая команда `fs_create_folder` (валидация имени и коллизий — на бэкенде), ошибка показывается в существующем стиле (`.tree-error`); новых IPC-команд нет. После успешного создания дерево обновляется и новая папка раскрывается. Строки папок в режиме списка перетаскиваются указателем так же, как файлы (тот же `usePointerDrag`): дроп в себя и в собственные подпапки запрещён (подсветка `.no-drop`), бэкенд `fs_move` дополнительно блокирует перенос в себя/подпапку и разрешает коллизии имён. После успешного переноса раскрытые папки и их закэшированное содержимое перенумеровываются на новые пути: перемещённая папка и всё её раскрытое поддерево остаются раскрытыми, а выделение (сама папка или её содержимое) следует за новым путём. Клик-раскрытие/выделение, двойной клик, контекстное меню, переименование и удаление сохраняются.

### 4.3 Задачи

- Source of truth — SQLite; UI: канбан из трёх колонок (Новые / В работе / Готово) с перетаскиванием карточек между колонками (смена статуса); создание, редактирование текста (inline), удаление, статусы, теги, даты.
- Закрытые задачи не удаляются: остаются в БД (колонка «Готово») и участвуют в поиске — «что мы делали по X на прошлой неделе» работает по закрытым тоже.
- Автоэкспорт/обновление md-файлов в `tasks/` проекта (переносимость, ручной просмотр).
- Агент может создавать, править, закрывать задачи.
- **Комментарий к задаче:** у каждой задачи — текстовый комментарий-заметка (создание и редактирование с карточки, кнопка-«облако»; пустой — удаляется). Отображается на карточке под датой. Агент читает и пишет комментарии как часть CRUD задач.
- **Напоминания и дедлайны:** у задачи — дата (дедлайн) + опциональное время напоминания; ставятся на карточке (календарик) или фразой в чате («напомни завтра в 10 связаться с заказчиком» — агент создаёт/обновляет задачу с напоминанием). В назначенное время — наттивное уведомление macOS; технически — одноразовая `notify`-задача планировщика (5.3), хранится в SQLite вместе с задачей.
- **Дедлайн-время (`dueTime`):** у задачи, кроме даты дедлайна, есть дедлайн-время в формате HH:MM — редактируется в форме создания и в редакторе срока на карточке рядом с датой. Если время не задано — по умолчанию **07:00** (по времени системы; существующим задачам проставляется миграцией). Время показывается рядом с датой на карточке канбана и в строках «Сегодня». Просрочка считается по **дате + времени**: задача просрочена, когда `дата+время < текущий момент` (локальное время), а не по дате целиком; это касается бейджей проектов, «Сегодня», поиска и счётчиков.
- **Просроченное видно сразу:** карточка просроченной задачи в канбане — красная дата + красная рамка; на карточке проекта в списке слева — красный бейдж «N просрочено» (сегодняшние — серый счётчик). Пропущенные при закрытом приложении напоминания считаются в бейдже с момента запуска — ничего не «теряется до следующего открытия проекта».
- **Метка «Просрочено»:** под заголовком/текстом карточки просроченной задачи — ненавязчивая красная подпись «Просрочено» (красный токен `--danger`, маленький шрифт, без тяжёлого бейджа/фона). Ставится строго по флагу `overdue` (просрочка по дате+времени, см. пункт про `dueTime`), поэтому граница «сегодня 06:59 vs 07:01» уже учтена этим флагом. Подпись дополняет красную дату/рамку, а не дублирует их; строки поиска и блоки «Сегодня» уже имеют свои индикаторы просрочки и не плодятся второй подписью.
- **Флаг приоритетности (`isPriority`):** задача может быть помечена «приоритетная» (важная) не только при создании (чекбокс в форме колонки), но и **постфактум** — в редакторе деталей карточки (кнопка «Приоритет, повтор, чек-лист»), где чекбокс можно ставить и снимать в любой момент. Флаг сохраняется через `task_update` (`isPriority: true|false`; `null`/отсутствие поля сохраняет текущее значение) и доступен агенту (`task_update` / `crm_task_update`). Карточка приоритетной задачи в канбане — с красной рамкой; флаг попадает во frontmatter экспорта `tasks/*.md` (`is_priority`).
- **Редактирование задачи агентом (in-place):** агент правит **существующую** задачу инструментом `task_update` (агент проекта) / `crm_task_update` (харнес) — переименовывает (title), меняет дедлайн-дату (`dueDate`) и дедлайн-время (`dueTime`), комментарий, `isPriority`, повтор (`recurrence`), чек-лист, напоминание (`remindAt`); отсутствующие поля сохраняют текущее значение, явный `null` у `comment`/`dueDate`/`remindAt` очищает их (`dueTime: null` тоже сохраняет текущее время). Статус меняется отдельным `task_move`/`crm_task_move`. Агент **не должен** «создать новую — удалить старую» вместо правки: id задачи сохраняется, количество задач не меняется, правка попадает в стек отмены (`undo_last` восстанавливает снимок задачи до изменения).
- **Таймер задачи (стенные часы):** у задачи накапливается затраченное время (`spentMs` — накопленные миллисекунды, `startedAt` — метка активного отсчёта в epoch-мс либо `null`). Отсчёт **начинается при переходе в «В работе»** (включая создание задачи сразу в этой колонке), **останавливается при переходе в «Готово» или возврате в «Новые»**, при повторном возврате в «В работе» **продолжается с накоплением** (не обнуляется). Время идёт по **стенным часам**: метки хранятся как epoch-мс (UTC), отсчёт продолжается при закрытом приложении; строковые дата/время в таймере не участвуют. Переходы статуса засчитываются в одном централизованном месте (канбан-дроп, `task_move`/`crm_task_move`, создание в «В работе», отмена/повтор) — двойного счёта нет; отмена (`undo_last`) восстанавливает таймер вместе со снимком задачи. **Миграция v33:** существующим задачам в «В работе» отсчёт стартует с момента миграции (`startedAt = now`), накопленное до этого считается нулевым. На карточке — футер внизу: тонкая отбивка и ненавязчивый нежирный текст `Затрачено на задачу: ЧЧ:ММ:СС`; для задачи «В работе» счётчик тикает раз в секунду (по стенным часам, без перерисовки всей доски), для остановленных — статичный итог; при нуле и незапущенном отсчёте футер скрыт. У завершённых задач **нет зачёркивания** заголовка (приглушённый цвет остаётся).
- **Переход и фокус задачи из «Сегодня»:** клик по задаче в блоках «Просрочено», «Скоро (7 дней)» и в других задачах экрана «Сегодня» открывает её проект, переключает на вкладку «Задачи» и **фокусирует** карточку в канбане: карточка **поднимается вверх своей колонки** (временная сортировка только для вида, пока задача сфокусирована — порядок в БД и дробные `position` не меняются), доска **прокручивается** к ней (`scrollIntoView`) и карточка **мягко пульсирует ровно 3 раза** (CSS-анимация на `box-shadow`/`outline`, без сдвига вёрстки после окончания; при `prefers-reduced-motion` пульс выключен, но подъём и прокрутка остаются). Снятие фокуса (таймаут подсветки или смена вкладки) возвращает исходный порядок по `position`. Фокус **не должен ломать перетаскивание**: на время активного драга временная сортировка отключается, и расчёт новой `position` опирается на **реальные** позиции соседей, а не на вид. Тот же путь навигации (`requestTask` → `pendingTaskId`, потребление в `FilesPanel`) используется и для кликов из палитры команд, и для результатов поиска по задачам; повторный клик по уже открытой задаче снова фокусирует и пульсирует. Не-задачные ссылки «Сегодня» (заметки, чаты, расписания) ведут себя как раньше.
- **Шапка экрана «Сегодня»:** в шапке — только заголовок с датой, строка-состояние под ним и кнопка «Обновить». Верхние сводные плашки-счётчики («Просрочено», «На неделе», «Расписаний», «Целей в работе») с экрана **убраны** и не рендерятся; счётчики остаются только в заголовках соответствующих карточек.
- **Перестановка карточек «Сегодня»:** шесть карточек экрана «Сегодня» («Просрочено», «Скоро (7 дней)», «Расписания», «Цели», «Свежие заметки», «Последние чаты») можно перетаскивать, меняя их порядок. Драг начинается **за заголовок карточки** (в шапке — иконка-грип, курсор grab); драги, начатые на кнопках/инпутах внутри карточки, игнорируются, клики и ссылки внутри карточки сохраняются; Esc и `pointercancel` отменяют перетаскивание. Визуал — общий с перетаскиванием проектов/заметок/задач (`usePointerDrag`): призрак карточки наклонён на 4°, «поднят» с тенью (`.drag-ghost`), исходная карточка приглушена. Порядок **глобальный** (одинаков для всех проектов), хранится в `localStorage` под одним ключом как список стабильных id карточек (`overdue`, `soon`, `schedules`, `objectives`, `notes`, `chats`): неизвестные id при чтении игнорируются, отсутствующие дописываются в конце в порядке по умолчанию; индекс вставки зажимается в допустимые границы. Порядок восстанавливается при монтировании экрана; перестановка **не** перезагружает данные и **не** перемонтирует содержимое карточек (React-ключи по id карточки).

### 4.4 Поиск

- **Только per-проект** (сквозной поиск по всем проектам — в «Будущем»).
- Смешанный: FTS (по словам) + семантический (эмбендинги EmbeddingGemma 2, см. стек 2) по содержимому всех проиндексированных файлов, включая `datas.md`, задачи, имена файлов.
- **Поиск по задачам — семантический, включая закрытые** (колонка «Готово»): запросы вида «что мы делали по редизайну на прошлой неделе» находят задачи по тексту, тегам и датам (создания/закрытия), а не только открытые.
- **Мультимодальный поиск** (благодаря vision-энкодеру той же модели): картинки проекта (скрины, брендбуки, фото) индексируются визуальными векторами в то же пространство — ищутся и текстом («найди скрин главной страницы»), и по похожей картинке («похожие изображения»). Вложения из чатов индексируются наравне с файлами.

### 4.5 Индексация

- Триггеры: **авто-watcher** (notify) за рабочей директорией — файлы, добавленные руками в Finder, индексируются сами; плюс ручная кнопка «Переиндексировать» в настройках.
- Извлечение текста: локальные Rust-парсеры (docx/pdf/xlsx/md/txt).
- Картинки (png/jpg/webp/gif): индексируются vision-энкодером EmbeddingGemma 2 (вектор в то же 768-d пространство), без OCR.
- Правила (разумные дефолты, настраиваются в UI): исключать `.git`, `node_modules`, `.DS_Store`, кэши; лимит размера файла ~20 МБ; лимит извлечённого текста ~200К символов на файл.

### 4.6 Чат-агент проекта

- Один непрерывный чат на проект, без ниток. Боковая панель справа, свой системный промпт («ты ведёшь проект, ретроллишь…», полный текст промпта — часть реализации).
- Инструменты агента проекта:
  1. **Поиск + чтение**: семантический/FTS-поиск по индексу проекта (в т.ч. закрытые задачи), чтение файлов, листинг дерева;
  2. **Запись файлов**: создание/редактирование файлов и папок внутри проекта (с подтверждением опасных операций);
  3. **Задачи**: CRUD задач проекта;
  4. **datas.md**: ведение файла доступов (добавление/обновление записей).
- RAG по требованию: агент сам вызывает инструменты поиска, авто-подмешивания каждого сообщения нет.
- Вложения: картинки (с предпросмотром в чате, разбор через vision) и документы — см. 6.1.
- Контекст: автосуммаризация старых сообщений при достижении **80% окна контекста модели**. Размер окна берётся из ответа/метаданных модели (если модель его не возвращает — дефолт **100 000 токенов**, переопределяется в конфиге).

## 5. Вкладка «Харнес»

### 5.1 Экран

- Слева — список сессий (как в Kilo/Claude Code): можно создавать новые чаты-сессии, они независимы; связаны только общей памятью. Пользователь волен вести всё в одной сессии.
- **Кнопка нового чата (Q-21):** в шапке сайдбара сессий вместо прежней иконки-плюса без подписи — синяя скруглённая акцентная кнопка с белым плюсом и видимой подписью **«Новый чат»**. Обработчик создания сессии, порядок контролов и подсказки не меняются.
- Центр — чат с общим агентом; лента запусков (кто/когда/статус, раскрытие шагов и tool-calls).
- Панель расписаний: список задач с описанием расписания, вкл/выкл.
- **Автоудаление сессий** без активности **30 дней** (порог настраивается, можно отключить). Вместе с сессией удаляются созданные в ней расписания.

### 5.2 Агент

- Один общий агент харнеса (без пресетов в v1), свой системный промпт: «управляешь компьютером по запросам пользователя, можешь ставить расписания…».
- **Рабочая территория по умолчанию** — папка `Harness/` в рабочей директории (см. 3.1): туда пишутся файлы/скрипты/артефакты, если пользователь явно не укажет другой путь. При этом агент может работать по всему компьютеру (пути вне `Harness/` и `Projects/` — через подтверждения).
- **Временная зона**: все временные файлы агента (оба агента и MCP-процессы, где это применимо) — в `Harness/tmp/`, а не в системном `/tmp`: свалка остаётся видимой и в одном месте. Подпапки создаёт сам агент по задачам; очистка — кнопкой «Очистить tmp» и/или автостиранием артефактов старше N дней (настройка). Системный `/tmp` агентом не используется.
- Технически: для всех дочерних процессов (bash, MCP, браузер) переменные `TMPDIR`/`TEMP` подменяются на `Harness/tmp/` — утилиты сами пишут туда.
- Инструменты (копия возможностей современного coding-агента):
  1. **fs**: чтение/запись/поиск файлов по машине;
  2. **bash/терминал**: выполнение команд;
  3. **браузер через CDP**: headless/headful Chrome — загрузка, клики, скриншоты, извлечение текста;
  4. **CRM-инструменты**: поиск по индексу проектов, задачи, datas.md — агент думает терминами CRM, а не только файлами;
  5. **планировщик**: агент сам создаёт/редактирует свои расписания («каждый день в 10:00 присылай курсы доллара») + уведомления в приложение при срабатывании;
  6. **вложения**: приём файлов/картинок в чат с предпросмотром и разбором (vision/извлечение текста) — см. 6.1;
  7. **скиллы и MCP**: подгрузка скиллов по запросу и инструменты внешних MCP-серверов — см. 6.2.
- **Интернет-инструменты: скорость и качество (Q-18).** `websearch`, `webfetch` и `http_request` работают **внутри процесса на HTTP-клиенте `ureq`** — без `curl`, shell и дочерних процессов (и тот же набор `net_tools` переиспользует агент заметок, см. выше). Редиректы обходятся вручную (≤5) со **SSRF-проверкой каждого hops**, тело ограничено 2 MiB, текст — `max_chars`, HTML сворачивается в читаемый текст без внешних парсеров. Таймауты: **connect 5 с** (быстро падать на недоступном хосте) и **read 15 с** (не ломать медленные, но живые сайты). `websearch` (HTML-эндпоинт DuckDuckGo) разрешает редирект-ссылки `/l/?uddg=` в реальные URL, **дедуплицирует результаты по итоговому URL** (первое вхождение) и отдаёт не более `limit` (≤20). CDP-браузер **переиспользует один процесс Chrome** между вызовами (убивается по простою или ошибке), без лишних пауз: навигация ждёт `Page.loadEventFired`, ожидания поллят условие, а не спят вслепую. Имена инструментов, их схемы, форма результатов и тексты ошибок остаются стабильными.
- **Разрешения**: по умолчанию — подтверждения опасных операций (запись вне CRM-папок, bash, браузерные действия). В настройках — тумблер **полного автопилота** со всеми разрешениями (на усмотрение пользователя).
- **Память**: глобальная память (см. 6.3) — факты/предпочтения, которые агент ведёт инструментами remember/recall и подмешивает в любую новую сессию. Видна и редактируема в UI.

### 5.3 Планировщик и фон

- Расписания выполняются, пока приложение открыто; опция «запускаться с системой» (macOS LaunchAgent) — для работы расписаний без открытого окна.
- При первом напоминании приложение запрашивает системное разрешение на уведомления macOS.
- Пропущенные запуски (приложение было закрыто) выполняются при старте.
- Модель планировщика — по образцу Ouroboros (`tools/followup.py`, `supervisor/queue_schedules.py`): одноразовые задачи (`run_at`) + повторяющиеся (5-полевой cron + IANA-таймзона); жизненный цикл расписания (активно/пауза/готово/ошибка) видно в UI; связь «related / independent» — порождённая задача помнит, из какого запроса она, с исходной формулировкой; отдельный тип «notify» — уведомление в приложение без вызова модели.

## 6. Общие требования к агентам

- **Один агент-луп на Rust** для обеих вкладок; различия — конфигурация (системный промпт, набор инструментов, границы доступа).
- **Изоляция контекстов** (единственное общее — глобальная память, 6.3):
  - чаты разных проектов полностью раздельны: контекст, файлы, индекс и задачи проекта A агенту проекта B не видны;
  - сессии харнеса раздельны между собой и с чатами проектов;
  - один чат = одно обсуждение, но пользователю никто не мешает вести в одном чате всё подряд — это его решение;
  - перенос знания между изолированными контекстами — только через глобальную память (агент сам предлагает запомнить) или явную просьбу пользователя («учти, что в проекте X...»);
  - доступ агента проекта к чужим проектам — только по явной просьбе пользователя.
- Протокол: OpenAI-совместимый `chat/completions` с tool calling; поддержка streaming.
- Подтверждения инструментов — единый механизм (очередь подтверждений в UI).
- Все вызовы пишутся в журнал запусков (история tool-calls).
- Учёт токенов/стоимости — вне v1 («Будущее»).

### 6.1 Вложения в чатах (обе вкладки)

- В поле ввода чата — кнопка «скрепка» + drag&drop файлов прямо в область чата; можно приложить несколько файлов за раз.
- **Поле ввода:** textarea растёт вместе с текстом (старт ~3 строки, предел ~10 строк), дальше не растёт — текст скроллится внутри поля. Под полем — строка инструментов: слева «скрепка», справа маленькая «Очистить» (корзинка, очищает поле и вложения) и круглая синяя кнопка «Отправить» (белая стрелка в синем круге). Между ними — серая подсказка мелким шрифтом: «Shift+Enter — перенос строки, Enter — отправить». Отправка — Enter, перенос строки — Shift+Enter (как в мессенджерах).
- **Картинки**: предпросмотр вложения показывается в чатe (в поле — чип с миниатюрой, в сообщении — изображение). Агент разбирает их через vision-модель («расскажи, что на картинке»).
- **Документы** (docx/pdf/xlsx/md/txt и др.): в чипе/сообщении — имя и иконка; агент извлекает текст (те же Rust-парсеры, что и для индекса) и работает с содержимым («вот счёт, проверь и сохрани в проект»).
- **Сохранение**: по умолчанию вложение сохраняется в папку проекта `Входящие/` (создаётся автоматически), факт добавления записывается в спец-файл `INBOX.md` проекта (дата, имя, от кого/из какого чата, краткое описание агента). В харнесе — по указанному пользователем пути (или в `Входящие` выбранного проекта).
- Вложения попадают в индекс проекта и доступны поиску/агенту как обычные файлы.
- Ограничения: размер вложения — в рамках лимитов индексации (настраиваемо); отправка в vision — только при подключенной vision-модели (иначе агент честно сообщает, что изображение не разбирает, но сохраняет).

### 6.2 Скиллы и MCP-серверы (оба агента)

Механика — копия того, как это устроено в современных coding-агентах (Kilo/Claude Code).

**Скиллы:**
- Скилл = папка в `Settings/skills/<имя>/` с файлом `SKILL.md`: YAML frontmatter (`name`, `description`) + markdown-инструкции + опциональные ресурсы (скрипты, ссылки).
- Формат манифеста расширяем по образцу Ouroboros (`docs/CREATING_SKILLS.md`, `skill_loader.py`): три типа скиллов — **инструкция** (чистый markdown), **скрипт** (исполняемый, с `timeout_sec`), **расширение** (инструменты); в frontmatter — опционально `permissions` (какие инструменты скиллу можно), `env_from_settings` (какие секреты из конфига подать), `scheduled_tasks` (скилл может объявить своё расписание).
- В системный промпт агента всегда подмешивается только короткий список (name + description); полный текст скилла агент подгружает инструментом `skill` по мере надобности — экономия контекста.
- **Встроенные скиллы**: при релизе в приложение копируется полный набор скиллов coding-агента (ponytail, research, tdd, grilling, code-review и т.д.) в `Settings/skills/builtin/` как «встроенные» (обновляются с приложением), пользовательские — в `Settings/skills/user/`.
- **Создание скиллов**: агент умеет сам создавать/редактировать скиллы пользователя (скилл «создать скилл»); по инструкции/тексту из чата инструмент `create_skill` пишет валидный `SKILL.md` в `Settings/skills/user/` (валидация имени, конфликт со встроенными — отказ); пользователь может править файлы руками — watcher подхватывает. Политика `create_skill` — **check** (не skip): каждое создание скилла проходит через стандартный диалог подтверждений, «молчаливого» создания нет.
- **Авто-предложение скилла (Q20)**: если одна и та же сложная задача выполнилась **2 раза**, агент **предлагает** создать скилл; создаёт только после явного подтверждения пользователя.
  - **Сложный запуск**: успешно завершённый прогон (`finish`/`stop`) с **≥ 4** завершёнными вызовами инструментов (кроме `finish_task`) **или** длительностью **≥ 2 минут**. Тривиальные и отменённые прогоны не считаются.
  - **Подпись «той же задачи»**: нормализованный текст запроса пользователя (нижний регистр, схлопнутые пробелы, обрезка до 200 символов) + отсортированный набор имён инструментов + их количество → хеш. Запросы, отличающиеся только регистром/пробелами, считаются одинаковыми.
  - **Детектор повторов**: каждый сложный запуск увеличивает счётчик подписи в SQLite (таблица `skill_proposals`, миграция v35). Одна строка на подпись, **одно предложение на подпись** на всё приложение (дедуп по чатам/проектам).
  - **Предложение**: при втором появлении подписи — одноразовое сообщение ассистента в чате, где завершился второй запуск: по-русски, с именем скилла-кандидата, списком инструментов и текстом задачи; объяснено, как согласиться («да») и отказаться («нет»). Не показывается, если скилл-кандидат уже существует (встроенный/пользовательский) или подпись уже предлагалась/отклонена.
  - **Подтверждение**: пользователь отвечает «да» → агент вызывает `create_skill` → стандартный диалог подтверждений → скилл создаётся и появляется в списке. Отказ или игнор — ничего не создаётся, предложение больше не повторяется (без «пилинга»).
- **Импорт извне**: импорт скилла(ов) из папки, `.zip` или git-репозитория (выбор в UI или агентом); валидация frontmatter, проверка имени, место конфликта со встроенными.
- Управление: список скиллов в UI с тумблерами вкл/выкл; выключенные не попадают в промпт.

**MCP-серверы:**
- Конфиг `Settings/config/mcp.json`: имя сервера, транспорт — stdio (`command` + `args` + `env`) или HTTP/SSE (`url`); несколько серверов. Сторонний MCP-сервер — внешний процесс пользователя (может быть хоть на Python); само приложение от этого не зависит и Python не требует.
- Инструменты подключённых MCP-серверов появляются в tool-листе обоих агентов с префиксом сервера (`mcp_<сервер>__<инструмент>`); подтверждения подчиняются общему механизму разрешений.
- Харденинг по образцу Ouroboros (`mcp_client.py`): описания инструментов и результаты MCP считаются недоверенными данными (не инструкции); маскирование секретов в логах; SSRF-денолист для metadata-endpoint'ов (localhost/LAN разрешены).
- Управление: список серверов в UI (статус, ошибки запуска, тумблер вкл/выкл), hot reload конфига через watcher.
- **Добавление сервера из чата**: харнес-агент по инструкции пользователя добавляет MCP-сервер инструментом `mcp_add` (имя, транспорт stdio/http/sse, command/args/env или url/headers). Запись идёт в тот же `Settings/config/mcp.json` через общий механизм конфигов (без параллельного хранилища), затем реестр MCP перезапускается и статус обновляется. Валидация имени и транспорта, отказ при дубликате имени и SSRF-адресах; операция подтверждается общим механизмом подтверждений. UI настроек показывает новый сервер при следующем открытии/обновлении (события watcher).
- Ресурсы и промпты MCP-серверов — в «Будущем», в v1 только инструменты.

### 6.3 Глобальная память (общая для всех агентов и чатов)

- Единая база памяти в SQLite (`Settings/.db/`) — **одна на всё приложение**: чаты проектов и харнес видят её целиком. Это не раздельные памяти вкладок.
- Содержимое: факты о пользователе и мире («обращаться на „ты“, зовут Миха», «агента зовут Вася Пупкин», «предпочитает короткие ответы», «клиент X — аптечная сеть»), предпочтения, решения, уроки.
- Идентичность агента — часть памяти: имя агента и как обращаться к пользователю задаются в настройках (по умолчанию — «Агент» / «на ты») и живут в памяти; подставляются в системный промпт **любого** чата (проект и харнес).
- Запись: агенты ведут память инструментами `remember` / `recall` (и сами предлагают запомнить важное); пользователь может добавить/отредактировать/удалить любую запись в UI («Память»).
- Инъекция: релевантные записи памяти подмешиваются в контекст каждой новой сессии (имя агента/пользователя — всегда, остальное — по релевантности/поиску).
- Конфликт с фактами проекта: `datas.md` и файлы проекта — источник истины по проекту; память — про пользователя и общие вещи. Записи памяти про конкретный проект помечаются проектом и подсвечиваются в его чате.

### 6.4 Механика агент-лупа (заимствования из Ouroboros, MIT)

Эталон-репо лежит в `PROJECT-S/ouroboros/` (MIT, копировать можно с сохранением copyright-уведомления; сторонние vendor-ассеты `web/vendor/` не трогать). Берём идеи и отдельные реализации.

- **Только идеи, реализация — на Rust.** Ouroboros целиком на Python; **в Project S Python не используется вообще**: ни рантайма, ни питоновых зависимостей, ни subprocess-вызовов питона. Всё перечисленное ниже переписывается нативно на Rust в нашем агент-лупе. Клон `ouroboros/` — read-only справочник для разработки, в сборку приложения не входит.

- **Явное завершение ответа**: луп оканчивается только вызовом инструмента `finish_task(action=finish|stop, answer=…)`; каждый раунд latch-ится финальный текст как fallback-кандидат — луп не «угадывает», что модель закончила (`loop.py`, `loop_delivery.py`).
- **Инструмент = один источник истины**: одна декларация порождает и JSON-схему для модели, и валидатор аргументов хендлера (`additionalProperties:false`) — схема и обработчик не разъезжаются (`tools/control_subagent_spec.py`).
- **Каталог инструментов**: дубли имён — жёсткая ошибка; коллизии MCP/расширений — отбрасываются заметно; классы инструментов (read-only / parallel-safe / meta) + лимит длины результата у каждого инструмента; скрытый политикой инструмент показывает «скрыт: <причина>», а не UNKNOWN_TOOL (`tools/tool_catalog.py`, `tool_capabilities.py`).
- **Ленивое обнаружение инструментов**: в постоянном списке схем — только ядро, полный каталог — по запросу (`list_available_tools`/`enable_tools`); учитываем лимит провайдера на число схем (OpenAI ≈ 128) (`tools/tool_discovery.py`).
- **Двухуровневые разрешения**: статическая политика по каждому инструменту (`skip` / `check` / `check_conditional`) — read-only без подтверждений; опасные (bash, запись, браузер, MCP) — очередь подтверждений человеку (наше отличие от авто-LLM-вердикта Ouroboros) (`safety.py`).
- **Сжатие контекста с чекпоинтами** (реализация нашей автосуммаризации из 4.6): старые завершённые tool-блоки сворачиваются в саммари, сырые байты до сжатия — в content-addressed хранилище (доказательства восстанавливаемы); транскрипт append-only, чтобы не ломать prompt-caching (`context_compaction.py`, `transcript_prefix.py`).
- **JSON-конверт результата инструмента** с типизированными кодами ошибок (`tools/tool_result.py`).

### 6.5 Экран настроек

- Вход — шестерёнка в правом верхнем углу тулбара; модалка с боковой навигацией по разделам. Всё из этого редактируется и в UI, и правкой `Settings/config/*` руками (3.4).
- **Подписи к настройкам**: у каждой настройки — короткая однострочная подсказка, за что она отвечает (понятно даже неподготовленному пользователю); без простыней текста.
- **Модель**: OpenAI-совместимый endpoint + API-ключ (plaintext, см. 3.4). После ввода endpoint/ключа приложение само тянет список моделей с endpoint'а (`GET /models`) и предлагает выбор **селектом**. Если список не получено получить — поле свободного ввода с явной подсказкой: «Endpoint не вернул список моделей — впиши название вручную, узнай у провайдера». Окно контекста (дефолт 100 000) подтягивается автоматически для выбранной модели; если модель его не сообщает — ставится дефолт с подсказкой, пользователь может исправить руками. Кнопка «Проверить подключение».
- **Агент**: имя агента и как обращаться к пользователю (идентичность — часть памяти, 6.3); тумблер полного автопилота (5.2).
- **Индексация**: лимиты размера файла и извлечённого текста, список исключений, кнопка «Переиндексировать» (4.5).
- **Скиллы**: список с тумблерами вкл/выкл, метка «встроенный», импорт из папки/.zip/git (6.2).
- **MCP**: список серверов, статус/ошибки запуска, тумблеры, добавление сервера (6.2).
- **Память**: CRUD записей глобальной памяти (6.3).
- **Прочее**: порог автоудаления сессий (5.1), «Очистить `Harness/tmp/`» (5.2), «Резервная копия» (3.6), «Запускаться с системой» (5.3).

## 7. Нефункциональные требования

- **Офлайн**: приложение полностью работает без LLM (файлы, задачи, поиск по FTS; семантика — локальные эмбендинги). LLM нужен только для агентных ответов.
- **Производительность**: индексация 100 файлов типового проекта — секунды; поиск по индексу проекта — < 300 мс; запуск приложения — < 3 с.
- **Приватность**: данные не покидают машину, кроме фрагментов, отправляемых выбранному LLM-эндпоинту; эмбендинги — локально.
- **Надёжность**: SQLite в WAL-режиме; файловые операции агента — с подтверждениями; бэкап-архив восстанавливаемый.
- **Масштаб v1**: десятки проектов, сотни тысяч файлов в индексе, десятки Гб данных — без деградации поиска.
- **Резервирование**: кнопка экспорта архива; всё переносится копированием папки PROJECT-S (кроме API-ключа — он тоже в конфиге, т.е. переносится полностью).
- **Открытость хранения**: однопользовательское приложение — никаких скрытых от владельца файлов/папок; любые правки руками подхватываются (см. 3.1).
