# Обновления Project-S

## Для пользователей

Автоматических обновлений пока нет: новая версия ставится вручную поверх старой. Рабочая папка, проекты, заметки, настройки и скачанная модель эмбеддингов при этом сохраняются.

### Как проверить новую версию

1. Откройте раздел **Releases**:
   https://gitverse.ru/mibazarow/Project-S-local-CRM/releases
2. Посмотрите последнюю версию. Сейчас актуальна **1.0.7**. Если у вас старее — скачайте новый файл.
3. Полностью закройте Project-S (`⌘Q`), чтобы приложение не держало файлы.
4. Установите новую версию:
   - **macOS (Apple Silicon):** откройте DMG и перетащите Project-S в `Applications`, подтвердив замену.
   - **Windows 11 x64:** распакуйте ZIP и запустите новый установщик. Он поставится поверх текущей версии.
   - **Linux:** версия готовится, обновление будет через Flatpak/Flathub.
5. Запустите приложение.

Перед крупным обновлением полезно сделать резервную копию рабочей папки — особенно если в ней есть важные проекты. Обновление не удаляет данные, но миграции базы выполняются автоматически.

### Если macOS или Windows не запускают новую сборку

Сборки пока не подписаны и не нотаризованы.

- **macOS:** правый клик по **Project-S** → **Открыть**, либо **Системные настройки → Конфиденциальность и безопасность → Всё равно открыть**.
- **Windows:** SmartScreen → **Подробнее** → **Выполнить всё равно**.

### Что сохраняется при обновлении

- рабочая папка (по умолчанию `~/Documents/PROJECT-S`): проекты, файлы, заметки, задачи, Harness, настройки;
- база и конфиги внутри `Settings/`;
- скачанная модель эмбеддингов — если она на месте, заново качать не нужно;
- ваши LLM-провайдеры и ключи в рабочей папке.

Модель эмбеддингов (~300 МБ) в установщик не входит и скачивается отдельно. Если после обновления поиск работает только по словам — проверьте, что модель на месте, и дайте приложению скачать её заново.

### Если что-то пошло не так

- Не удаляйте рабочую папку: там все пользовательские данные.
- Не откатывайтесь на старую версию после миграции базы без резервной копии — старая версия может не открыть новую схему.
- Сначала восстановите рабочую папку из копии, затем запускайте приложение.

## Для разработчика

Текущее состояние: автообновления **не реализованы**. В проекте нет `tauri-plugin-updater`, `latest.json` и CI. macOS-сборка **ad-hoc и не нотаризована**, Windows-сборка **не подписана**. Обновление сейчас — ручное скачивание нового DMG/ZIP с GitVerse.

### Что нужно решить до автообновления

- **macOS:** сертификат **Developer ID Application**, hardened runtime, нотаризация и stapling. Apple Development для чужих Mac не подходит.
- **Windows:** подпись **Authenticode**, установка NSIS в режиме `currentUser`; обновление не должно требовать администратора.
- **Linux:** отдельный путь — Flatpak/Flathub, а не Tauri Updater.
- **CI/релизный скрипт:** сейчас всё собирается вручную; для автообновлений нужен воспроизводимый процесс сборки, подписи и загрузки артефактов.

### Особенности проекта, которые нельзя ломать обновлением

- Рабочая папка пользователя (`~/Documents/PROJECT-S` по умолчанию) — единственный источник данных; обновление не должно её трогать.
- SQLite-схема — **v40** с последовательными миграциями. Обновление только вперёд; даунгрейд после миграции не поддерживается.
- Модель эмбеддингов лежит в `Settings/models/embeddinggemma-2` и скачивается отдельно; не удалять её при обновлении.
- Windows-сборка идёт с macOS по SSH; см. `CROSPLATFORM.md`. Сборка/подпись Windows должна быть частью релизного процесса.
- GitVerse не принимает `.exe` и пробелы в именах ассетов: Windows публикуется ZIP-ом, имена файлов переименовываются. Для updater-артефактов это надо учесть заранее.

## Вариант 1. Уведомление о новой версии

Быстрый и безопасный шаг. Приложение проверяет JSON и показывает баннер со ссылкой на релиз; пользователь скачивает установщик сам.

Пример `latest.json`:

```json
{
  "version": "1.0.8",
  "date": "2026-11-01",
  "notes": "Что нового...",
  "url": "https://gitverse.ru/mibazarow/Project-S-local-CRM/releases/tag/v1.0.8"
}
```

Логика:

1. Раз в 12–24 часа и по кнопке «Проверить обновления» запросить JSON.
2. Сравнить `version` с текущей по semver.
3. Показать неблокирующий баннер: «Доступна версия 1.0.8» → «Скачать» / «Позже».
4. Ничего не перезапускать и не прерывать работу пользователя.

Плюсы: не нужны ключи обновлений, минимум риска.  
Минусы: установка вручную.

`latest.json` можно положить:

- raw-файлом в репозиторий (просто, но возможен кэш);
- ассетом релиза GitVerse;
- на статический хостинг / Cloudflare R2 / S3.

## Вариант 2. Полное автообновление через Tauri Updater

Tauri Updater умеет проверить версию, скачать артефакт, проверить подпись, заменить приложение и перезапустить его.

### 2.1. Ключ обновлений

Это отдельный ключ Tauri, не связанный с подписью Apple или Authenticode.

```bash
npx tauri signer generate -w ~/.tauri/project-s.key
```

- публичный ключ — в `tauri.conf.json`;
- приватный ключ — в CI/секретах и офлайн-бэкапе;
- в репозиторий не коммитить;
- потеря приватного ключа = невозможность обновить уже установленные копии.

### 2.2. Конфиг

```json
{
  "bundle": {
    "createUpdaterArtifacts": true
  },
  "plugins": {
    "updater": {
      "endpoints": ["https://example.com/project-s/latest.json"],
      "pubkey": "ПУБЛИЧНЫЙ_КЛЮЧ"
    }
  }
}
```

Для Windows-конфига (`tauri.windows.conf.json`) проверить, что updater-артефакт создаётся для NSIS и установка остаётся `currentUser`.

### 2.3. Сборка

macOS:

```bash
TAURI_SIGNING_PRIVATE_KEY="$HOME/.tauri/project-s.key" \
TAURI_SIGNING_PRIVATE_KEY_PASSWORD="..." \
npx tauri build
```

Нужны:

- `Project-S-1.0.8-macOS-ARM.dmg` — первая установка;
- `Project-S_1.0.8_aarch64.app.tar.gz` — автообновление macOS;
- `.sig` — подпись артефакта.

Windows (с macOS по SSH, по `CROSPLATFORM.md`):

- `Project-S-1.0.8-Windows-x64-Setup.zip` — первая установка;
- updater-артефакт Tauri для NSIS (`.nsis.zip`/`.exe`-формат зависит от версии Tauri) + `.sig`;
- если GitVerse не принимает формат, updater-артефакт выкладывать на статический хостинг, а в релиз — ZIP и `latest.json`.

### 2.4. `latest.json`

```json
{
  "version": "1.0.8",
  "notes": "Что нового...",
  "pub_date": "2026-11-01T12:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "signature": "СОДЕРЖИМОЕ_SIG",
      "url": "https://example.com/project-s/Project-S_1.0.8_aarch64.app.tar.gz"
    },
    "windows-x86_64": {
      "signature": "СОДЕРЖИМОЕ_SIG",
      "url": "https://example.com/project-s/Project-S_1.0.8_x64-setup.nsis.zip"
    }
  }
}
```

Linux-ключ `linux-x86_64` для Flatpak не использовать: обновления идут через Flathub.

### 2.5. Проверка в приложении

```rust
use tauri_plugin_updater::UpdaterExt;

let update = app.updater()?.check().await?;
if let Some(update) = update {
    // показать версию и notes,
    // после согласия: update.download_and_install(...).await?;
}
```

UX:

- проверка при запуске с задержкой и раз в 12–24 часа;
- «Проверить обновления» в настройках/меню;
- баннер «Доступна версия 1.0.8» → «Обновить» / «Позже»;
- прогресс загрузки и понятная ошибка;
- не перезапускать приложение, пока идёт работа агента, индексация или диалог;
- тумблер авто-проверки и канал `stable` / `beta`;
- перед установкой предупредить о миграции базы и предложить резервную копию рабочей папки.

### 2.6. Хостинг и GitVerse

- `latest.json` — raw-файл, ассет релиза или статический хостинг;
- macOS-артефакт — GitVerse Release или R2/S3;
- Windows-артефакт — с учётом запрета `.exe` и пробелов в именах;
- для Rust-запроса CORS не важен, но файл должен открываться без авторизации.

## Рекомендуемый порядок

1. **Сейчас:** вариант 1 — проверка `latest.json` и баннер со ссылкой на релиз.
2. **Перед production-релизом:** Developer ID + нотаризация macOS, Authenticode для Windows.
3. **После этого:** Tauri Updater для macOS и Windows.
4. **Linux:** Flatpak/Flathub, обновления силами пакетного менеджера.
5. **Позже:** канал beta, CI-сборка и автоматическая загрузка артефактов.
